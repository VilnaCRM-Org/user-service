# TEST image publisher

The proposed `publish-poc-images.yml` workflow belongs to the application repository and existing runtime PR492. It is an internal service-controller interface. Users keep the normal infrastructure PR-comment deployment flow; they do not dispatch images manually or copy receipt IDs.

The intended order is registry apply/drift and authenticated completion, automatic application publication, then reviewed workload planning and saved-plan apply. The automatic cross-repository dispatch grant and service controller connection are not installed by this application change.

The trusted service dispatcher must authenticate original registry completion and current deployment admission before calling the workflow on main. Its single `request` input is a closed JSON object containing `source_sha`, `platform`, `registry_phase_receipt_id`, `registry_contract_digest` and `registry_checkpoint_version`. The application accepts only the existing evidence App's native run actor and triggering actor, main workflow, first attempt, and an application source commit equal to the native workflow run SHA. If main advances between dispatch preparation and workflow creation, admission stops before build or AWS credentials. The application consumes this App attestation; it does not independently download service artifacts. The infrastructure consumer independently verifies the original registry receipt again.

`Validate application release` runs the normal `make start`, `make ci` and clean-source check without AWS credentials. `Build application images` starts on a fresh `ubuntu-latest` runner and builds `frankenphp_prod` and `app_workers` from the admitted source. Decision D-18 fixes one image architecture, `linux/amd64` (ECS `X86_64`), for every environment, TEST and PROD: there is no arm64 build, no multi-arch publishing and no OCI image index. Any other platform, including `linux/arm64`, is rejected at publisher request validation (`publisher-platform`) before native build or credentialed publication. Each target is built with `--platform linux/amd64 --provenance=false --sbom=false`. BuildKit attestations are disabled because an attached provenance or SBOM attestation turns the result into an image index (image manifest plus attestation manifest), which would be pushed as an index instead of a single-image manifest; release evidence is carried by the publisher's own provenance artifact instead. A builder whose `docker build` does not offer both flags, such as the legacy builder, stops the build (`publisher-attestation-flags`) rather than silently building with default attestations. Every saved archive must contain exactly one image manifest, or the build, the pre-credential `prepare` step and `publish` refuse it (`publisher-archive-not-single`); the same three points refuse a saved image whose config is not `linux/amd64` (`publisher-platform`). The shared release-manifest codec accepts only `linux/amd64` as well: building, decoding or producing release evidence for any other platform, including `linux/arm64`, is refused with reason `platform`. On any failure the publisher prints exactly one line, `Image publishing failed: <reason>`, with `<reason>` taken from the closed `REFUSAL_REASONS` set in `scripts/poc_image_publisher.py` (for example `publisher-manifest-not-single`, `publisher-attestation-flags`, `publisher-archive-not-single` or `publisher-platform`); a failure outside that set prints `publisher-unclassified`, and no exception text, path, token or AWS output is printed. It does not execute application Make scripts with AWS credentials. The image transfer artifact contains exactly `build.json`, `web.tar` and `worker.tar`; each tar is bounded at 3GiB and the ZIP at 7GiB.

`Publish TEST application images` starts on another fresh runner in `poc-test-images`. Before OIDC it validates completed native jobs, exact immutable transfer bytes and metadata, App delegation, and the native environment's main-only branch, disabled administrator bypass and independent Kravalg review policy. It assumes only `user-service-test-ImagePublisher` in TEST. It pushes the two fixed TEST ECR repositories and reads each image back with `describe-images`. The readback must report a single-image manifest (`imageManifestMediaType` of `application/vnd.docker.distribution.manifest.v2+json` or `application/vnd.oci.image.manifest.v1+json`), an image config artifact type and no referrer subject. An image index, manifest list, attestation manifest or missing media type fails closed as `publisher-manifest-not-single` (D-18) before any release evidence is written. The publisher then uploads provenance, quality evidence and the versioned release manifest. No infrastructure apply role, static AWS key or App private key is used by this workflow.

The fixed artifacts are `poc-build-provenance-{run_id}-1` (`provenance.json`), `poc-quality-evidence-{run_id}-1` (`quality.json`) and `poc-release-manifest-{run_id}-1` (`release-manifest.json`). The infrastructure consumer resolves the last artifact from the publisher run already bound in the reviewed release contract, then checks its original workflow/jobs and exact decoded manifest. A digest-shaped string alone is not authenticated image evidence.

Run the focused offline contracts with `make test-poc-publisher`. These tests use simulated GitHub/AWS responses and real local subprocess boundary checks. They do not prove native image builds, ECR publication, workload health, PROD promotion or rollback. Normal application CI, applicable skill/BMAD gates and native acceptance remain required before this draft is ready. The existing App dispatch capability, trusted workflow installation, protected environment and central OIDC permissions must be installed and verified before any credentialed execution.
